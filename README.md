**1인 가구를 위한 밀키트 커머스 플랫폼**

기획·문제 정의부터 백엔드 API, 프론트엔드, AWS 인프라, 배포 자동화까지 1인 개발로 구축했습니다.

## 1. 문제 정의

최초 가설은 "1인 가구는 식재료 판매 단위가 커서 불편하다" 였습니다.
코드를 쓰기 전에 검증하기로 하고, 세 곳(아파트 커뮤니티 2곳, 부트캠프 1곳)에서 66명 설문을 진행했습니다.
**"집에서 요리를 잘 하지 않게 되는 가장 큰 이유"** (복수응답, n=65)

| 응답 | 인원 | 비율 |
|---|---|---|
| 조리 과정의 번거로움 | 40 | 61.5% |
| 남은 식재료 폐기 부담 | 24 | 35.4% |
| 배달·외식이 더 저렴해서 | 12 | 18.5% |
| 식재료 단위가 너무 커서 | 4 | 6.2% |

제가 기획 단계에서 세운 가설은 4명이 선택한 항목이었습니다. 가설이 틀렸다고 판단하고 문제를 '양'이 아니라 '수고'로 재정의했습니다.
> 사용자가 간편하게 꽉찬 밀키트를 먹을 수 있도록 하는 것이 목표였습니다.<br/>
이 기준으로 제품 방향과 도메인 모델, API 설계를 다시 잡았습니다.

## 3. 주요 기능

- **상품 검색** — Elasticsearch + Nori 기반 형태소 검색, 사용자 사전 적용
- **미드나이트 타임딜** — 저녁 10시까지 남은 시간 표시하여 저녁 10시에 한정 수량 상품 판매. 동시성 제어의 검증 대상 
- **장바구니 / 주문** — 상품별 수량 상한 처리
- **회원 / 인증** — JWT 기반 Stateless 인증, Google OAuth2 연동
- **리뷰** — 로그인 사용자 작성
- **관리자** — 상품·재고 관리
- **구독** - 주간 사이클 스케줄 — 마감 → 일괄 결제 → 실패 시 결제수단 변경 안내 → 재시도 → 최종 실패 시 해당 회차만 건너뛰고 구독 유지, 구독 + 단품 병행 구조
- **쿠폰** - 4주연속 구독시 무료 배송 쿠폰

*(구독 결제와 쿠폰 발급 파이프라인은 개발 고도화중)*

## 4. 기술적 고민과 트러블슈팅

### 4-1. 순간 트래픽에서의 재고 정합성

**문제** — 타임딜 오픈 시 한정 수량 상품에 요청이 몰리면 재고 초과판매(oversell)가 발생할 수 있습니다.
**판단** — DB 비관적 락을 먼저 검토했으나, 락 대기 시간만큼 커넥션을 점유하기 때문에 순간 트래픽에서는 커넥션 풀 고갈로 이어진다고 판단했습니다. 재고 차감을 DB 밖으로 빼기로 했습니다.
**설계**

1. Redis Lua 스크립트로 재고 확인과 차감을 **하나의 원자적 연산**으로 처리하는 단일 게이트 구성
2. 게이트를 통과한 요청만 DB 주문 트랜잭션 진입
3. DB 트랜잭션 실패 시 **Redis 재고를 복원하는 보상 로직**으로 두 저장소 간 정합성 유지

두 저장소를 쓰는 이상 정합성이 깨지는 창은 반드시 생기므로, 그 창을 어떻게 닫을지를 함께 설계해야 한다고 봤습니다.

**검증** — k6로 재고 100개 상품에 동시 1,000요청 부하 테스트

| 항목 | 결과 |
|---|---|
| 주문 성공 | 정확히 100건 |
| 최종 Redis 재고 | 0 |
| 초과판매 | 0건 |

### 4-2. 형태소 분석기 오분석 추적

**문제** — 기존 `LIKE` 검색은 인덱스를 타지 못하고, 어순이 다르면 검색이 실패했습니다. Elasticsearch와 Nori를 도입했으나 결과가 예상과 달랐습니다.

**추적** — `_analyze` API로 토큰 단위 검증 중 두 가지 오분석을 발견했습니다.

| 입력 | 분석 결과 | 문제 |
|---|---|---|
| `1인가구` | `1` / `인` / `가구` | 핵심 키워드가 무의미하게 분해 |
| `무항생제` | `항생제` | 접두사 유실로 **의미가 반전** |

'무항생제' 상품을 찾는 사용자에게 '항생제' 관련 상품이 매칭되는 상황이었습니다.

**해결** — 사용자 사전을 적용하되, 도메인 특성에 따라 토큰화 기준을 차등 적용했습니다.

- `1인가구` → 복합어로 묶음 (분해되면 의미 소실)
- `무선이어폰` → 분해 허용 ('이어폰' 검색에 잡혀야 함)

**추가 설계** — 프리티어 EC2에서 Elasticsearch 최소 힙 1GB라는 제약을 사전에 인지하고, `ProductSearcher` 인터페이스로 검색 엔진을 추상화했습니다. 설정값 하나로 엔진을 전환하며 동일한 API로 두 구현을 비교 검증할 수 있습니다.

### 4-3. DNS 위임 체인 추적 (HTTPS 발급 실패)

**문제** — EC2 + Nginx 환경에서 Let's Encrypt 인증서 발급 시 도메인 검증 타임아웃이 반복됐습니다.
**과정** — DNS 콘솔에서 레코드를 고쳐가며 재시도하는 방식으로는 원인에 닿지 못했습니다. 조작을 멈추고 `dig +trace`로 루트 서버부터 위임 체인을 추적했습니다.
**원인** — 권위 네임서버가 AWS Route 53으로 이관되어 있어, 레지스트라와 실제 호스팅 주체가 이원화된 상태였습니다. 레지스트라 쪽 콘솔에서 수정한 레코드는 실제 질의 경로에 반영되지 않고 있었습니다.

**해결** — Route 53에서 레코드를 정정해 인증서를 정상 발급받았고, systemd timer 기반 90일 자동 갱신 파이프라인을 구성해 수동 갱신 작업을 없앴습니다.

### 4-4. 무중단 배포와 502 오류

**문제** — 신규 기능 배포 시 서비스 다운타임이 발생했습니다.
**해결** — GitHub Actions와 Nginx 기반 Blue/Green 배포를 구성했습니다. `app-blue` / `app-green` 두 컨테이너를 두고, 신규 버전의 헬스체크 통과를 확인한 뒤 트래픽을 전환합니다.
**트러블슈팅** — 구성 직후 배포 중 502가 간헐적으로 발생했습니다. nginx reload 시점과 신규 컨테이너 기동 완료 시점의 순서 문제였고, 전환 순서를 조정해 해결했습니다. 인프라 복잡도는 늘었지만 배포 리스크와 사용자 영향도를 줄이는 트레이드오프를 택했습니다.

### 4-5. AI 제안을 로그로 교차 검증

CI/CD 시크릿 주입 오류를 LLM 제안대로 고쳤을 때 문제가 재현되지 않았습니다. 제안을 채택하는 대신 워크플로우 로그를 직접 추적해, 워크플로우가 아니라 shell 단계의 변수 치환이 원인임을 확인했습니다. 초기 코드와 로그 1차 분석에는 LLM을 활용하되, 원인 가설은 실제 로그와 교차 검증합니다.
초기 코드 작성과 에러 로그 1차 분석에는 LLM을 활용하되, 원인 가설은 반드시 실제 로그와 교차 검증하는 방식으로 작업합니다.
